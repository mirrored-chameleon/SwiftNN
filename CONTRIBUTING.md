# Contributing to SwiftNN

## Welcome 🎉

Hello, and thank you for your interest in contributing to SwiftNN!

We’re excited to see what you can build, improve, experiment with, and discover
using this library.

You don't need to be an expert to contribute. Bug reports, documentation
improvements, tests, ideas, and code contributions are all valuable and can
help make SwiftNN better.

Here are a few things to know before you get started.

## Before You Contribute 🧭

Before contributing, please:

- Read the [Code of Conduct](CODE_OF_CONDUCT.md).
- Check existing issues and discussions before reporting a new issue, so we
  can avoid duplicates.
- For large or significant changes, consider opening a discussion or issue
  first so the idea can be discussed before implementation.
- Make sure you understand the purpose and potential effects of any changes
  you make to the codebase.

SwiftNN is open to significant improvements and new ideas. Large changes are
welcome when they provide a meaningful improvement to the project.

## Ways to Contribute 💡

There are many ways to contribute to SwiftNN.

You can:

- Fix bugs
- Add features
- Improve performance
- Write or improve tests
- Improve documentation
- Improve examples
- Report bugs
- Suggest new ideas
- Review pull requests
- Improve the developer experience

Contributions don't have to be huge. Even a small improvement can make a
difference.

If you see something that could be better, feel free to help improve it.

## Reporting Issues 🐛

If you encounter a problem with SwiftNN, please report it through the
[Issues](../../issues) tab.

When reporting an issue, provide as much relevant information as possible,
including:

- A clear description of the problem
- What you expected to happen
- Steps to reproduce the issue
- Your Swift version
- Your platform and operating system
- Relevant error messages or logs
- A minimal example, when possible
- Anything else that may help us reproduce and understand the problem

### Bug Reports 🔎

When reporting a bug, please explain what went wrong and provide enough
information for someone else to reproduce it.

A good bug report can save a lot of time when trying to track down the cause.

### Feature Requests ✨

Have an idea for SwiftNN? We'd love to hear it!

You can discuss ideas through the
[Swift Forums](https://forums.swift.org/t/swiftnn-a-cross-platform-machine-learning-library-for-swift/89305)
or start a discussion directly on GitHub.

When suggesting a feature, explain what problem it would solve, why it would
be useful, and how you think it could improve SwiftNN.

## Pull Requests 🚀

Pull requests are one of the main ways SwiftNN grows and improves.

### Creating a Pull Request

When creating a pull request, please explain:

- What the change does
- Why the change is being made
- What parts of SwiftNN are affected
- Any potential compatibility or performance impacts
- How the change improves SwiftNN
- Any tests you have added or performed

Please keep your pull request focused where possible. Unrelated changes can
make a contribution harder to review.

### Pull Request Expectations 🧪

Pull requests should aim to **add to and improve SwiftNN, not unnecessarily
break or destabilize it.**

We welcome contributions of all sizes, including substantial rewrites and
architectural changes. A large change is not a bad change if it meaningfully
improves the project.

Good pull requests should, where reasonably possible:

- Contain clear, readable, and maintainable code
- Work as intended
- Avoid knowingly breaking existing functionality
- Include appropriate tests for new or changed functionality
- Follow SwiftNN's existing conventions where appropriate
- Avoid unrelated changes
- Clearly explain significant design decisions

A pull request does not need to be perfect before it is submitted. Feedback,
discussion, and requested changes are a normal part of the review process.

However, deliberately destructive changes, intentionally broken code, or
contributions that repeatedly and unnecessarily harm the project are not
acceptable.

## Breaking Changes ⚠️

Breaking changes can sometimes be necessary, especially as SwiftNN evolves.

If your contribution breaks existing functionality or changes a public API,
please clearly explain what is changing, why it is necessary, and what the
impact may be.

Breaking something accidentally is not the same as deliberately damaging the
project. Mistakes happen, and contributors are encouraged to work with
maintainers to fix them.

Repeatedly submitting intentionally harmful changes or ignoring reasonable
maintainer requests may result in moderation under the
[Code of Conduct](CODE_OF_CONDUCT.md).

## Testing 🧪

Testing helps make sure changes actually work and don't accidentally break
something else.

Please test your changes before submitting a pull request whenever possible.

Tests can include:

- Swift package tests
- Small programs using SwiftNN
- Example applications
- Performance tests
- Experiments using SwiftNN
- Tests in your own repository

If you find that a change needs a new test, feel free to add one.

SwiftNN's test suite will continue to grow as the project develops.

## Documentation 📚

Good documentation is an important part of a good open-source project.

When writing or changing documentation, try to keep it:

- Clear
- Concise
- Accurate
- Easy to understand
- Up to date

If your change adds or changes public functionality, please update the
relevant documentation or examples where appropriate.

## Code Style 🧹

Please try to keep SwiftNN's code clean, readable, and maintainable.

When contributing code:

- Follow Swift's established naming conventions
- Prefer readable code over unnecessarily clever code
- Keep code focused and understandable
- Avoid unnecessary duplication
- Avoid unnecessary dependencies
- Follow existing SwiftNN patterns where they make sense

SwiftNN aims to remain lightweight and easy to use, so new external
dependencies should have a strong technical reason behind them.

## Review Process 👀

Pull requests will be reviewed by the project maintainer and, where
appropriate, other contributors who have been trusted to help review changes.

Reviewers may:

- Ask questions
- Request changes
- Suggest alternative approaches
- Point out potential problems
- Approve the pull request
- Decide that a change is not currently suitable for SwiftNN

Opening a pull request does not guarantee that it will be merged.

The goal of review is not simply to reject changes. It is to help make
SwiftNN better and ensure that contributions fit the project's goals.

## Code of Conduct 🤝

Please read and follow the
[Code of Conduct](CODE_OF_CONDUCT.md) when participating in the SwiftNN
community.

Contributing to SwiftNN means helping create an open, welcoming, and
constructive community.

## Thank You 💙

Thank you for contributing to SwiftNN!

Whether you've fixed a typo, reported a bug, improved a mathematical
implementation, written documentation, added a new feature, or completely
rewritten a component for the better, your contribution can help move the
project forward.

Keep your changes thoughtful, clean, and worthwhile.

We're excited to see what you build.

**Welcome to the SwiftNN community! 🚀**
